#Installation and environment

For security, Toss Payments APIs communicate only over TLS 1.2 or later. If your server environment does not support TLS 1.2, the connection is dropped during the handshake when you call the API.

A version that supports TLS 1.2 is not the same as a connection that actually uses TLS 1.2. Many integrations fail because the version meets the requirement but the default is still TLS 1.0, so check both the minimum requirements and whether additional configuration is needed.

Note The minimum requirement is the lowest version that can communicate over TLS 1.2. With the recommended version, you can integrate without additional configuration.

XPayClient 4.1.0.0 comes in two builds; use the one that matches the JDK on your server. Both builds have the same public API and produce the same hash values, so you do not need to change your integration code.

java

Note If keystore_cacerts_dir in mall.conf is empty, XPayClient 4.1.0.0 verifies the server certificate with the default JDK cacerts. Set the path only when you use a separate truststore. If the file at the specified path does not exist, requests fail with response code 20101.

#PHP environment

For PHP, the OpenSSL version PHP is compiled with matters more than the PHP version. TLS 1.2 requires OpenSSL 1.0.1 or later, so upgrading PHP alone may not solve the problem.

#Supported versions

VersionSupportDescription
PHP 5.4 or earlier❌There is no way to specify TLS 1.2.
PHP 5.5⚠️Adds the TLS 1.2 constant. Requires cURL 5.5.19 or later.
PHP 5.6✅Automatically negotiates the highest TLS version, and certificate verification is enabled by default.
PHP 7 or later✅Works without additional configuration.
Note On PHP 8, use the XPayClient 4.1.0.0 PHP library. The 4.0.0.x PHP library cannot be loaded on PHP 8.0 or later because of syntax errors. Version 4.1.0.0 works on PHP 5.6 through 8.x.
Caution If your environment uses OS default packages, as on CentOS 6, always check the OpenSSL version. Upgrading PHP does not help if OpenSSL is outdated.

#ASP environment

Classic ASP has no TLS stack of its own. MSXML2.ServerXMLHTTP and WinHttp.WinHttpRequest.5.1 use Windows WinHTTP and Schannel directly, so operating system settings determine whether TLS 1.2 is supported.

#Install the library

The install/XPayClientForCOM folder of the ASP sample (xpay-samples/asp) contains the COM component XPayClientCom.dll. Choose the DLL that matches your server environment and register it.

text
install/XPayClientForCOM/
├── X64/
│   ├── MD/XPayClientCom.dll

#MT and MD builds

MT and MD indicate how the C runtime library (CRT) was linked when XPayClientCom.dll was built. The functionality is the same; only the components required on the server differ.

FolderCRT linkingServer requirements
MTStatic linking. The CRT is included in the DLL.Works without additional installation.
MDDynamic linking. Loads the CRT from external DLLs provided by Microsoft.The Visual C++ Redistributable package of the version the DLL was built with must be installed on the server. The package architecture (x64 or x86) must also match the selected folder.

Use the MT build unless you have a specific reason not to. The MD build requires the Visual C++ 2008 Redistributable (msvcr90.dll, mfc90u.dll). Use the MD build only if the matching redistributable package is already installed and maintained on the server. Without the redistributable package, installing the COM+ component or creating the object with Server.CreateObject fails because the DLL cannot be loaded.

Note MT and MD are options Toss Payments uses when building the DLL. ASP loads the finished COM component, so you do not need to match build options or recompile the DLL.

#Installation steps

  1. Choose the folder (X64 or X86) that matches the bitness of the server OS and the IIS application pool, and then select XPayClientCom.dll from the MT or MD build in that folder.
  2. Copy the selected DLL to a permanent location. COM+ remembers the file path at registration time, so you cannot create the object if you move or delete the DLL after registering it.
  3. Register the component in Component Services by following the COM+ registration steps below.
  4. Place the lgdacom/conf folder in a path that is not accessible from the web, and set the merchant ID and mertkey in mall.conf. For details, see Configure conf files.

After registration, create the object in your ASP page with Server.CreateObject("XPayClientCOM.XPayClient").

For the complete file structure of the sample package, see Sample file structure.

#COM+ registration

Register XPayClientCom.dll as a COM+ application in Windows Component Services. The steps below are based on the Windows Server 2012 screens; the menus are the same in Windows Server 2008 R2 and later. Use an account with administrator privileges.

#1. Create an empty COM+ application

  1. Open Control Panel > Administrative Tools > Component Services.
  2. In the left tree, select Component Services > Computers > My Computer > COM+ Applications, right-click, and select New > Application.
  3. When the COM+ Application Install Wizard opens, click Next and select Create an empty application.
  4. Enter XPayClientCom as the application name, select Server application as the activation type, and click Next.
  5. In the account settings, select Network Service - Built-in service account with network access and click Next.
  6. Leave the Add Application Roles screen as is and click Next. The default CreatorOwner role is all you need.

#2. Add Authenticated Users

  1. On the Add Users to Roles screen, select Users under CreatorOwner and click Add.
  2. In the Select Users or Groups window, click Advanced > Find Now.
  3. Select Authenticated Users in the search results and click OK. Confirm that it appears in the object names to select, and click OK again.
  4. Confirm that Authenticated Users appears under Users, and click Next > Finish.

#3. Install the XPayClientCom.dll component

  1. Expand XPayClientCom under COM+ Applications, right-click Components, and select New > Component.
  2. In the COM+ Component Install Wizard, click Next and select Install new component(s).
  3. Click Add, select the XPayClientCom.dll you copied earlier, and click Open.
  4. If the DLL is valid, XPayClient appears under the components found, with interfaces shown as Yes. Click Next > Finish.

#4. Verify the registration

  1. Check that the function list appears under the methods of XPayClientCom > Components > XPayClient.
  2. Right-click XPayClientCom, select Shut down, and then select Start. If no error dialog appears, the component is registered correctly.
Note Windows Server 2003 does not support TLS 1.2 and cannot be integrated. Check Supported versions above first.

#Notes

  • System locale: The COM component converts request values with the Windows system code page and sends them as EUC-KR. If the server's system locale is not Korean (code page 949), Korean request values are corrupted.
  • UTF-8 pages: The sample pages are written in UTF-8 and processed as UTF-8 through <%@ CodePage=65001 %> on the first line and Response.CharSet = "UTF-8". The COM component returns Korean text in responses as is, so it displays correctly regardless of output_UTF8.
  • LGD_ENCODING: Because the COM component sends requests as EUC-KR, do not set LGD_ENCODING to UTF-8 in API requests. The LGD_ENCODING parameter of the payment window is unrelated.
  • Comparing return values: Init, Init_TX, and TX return 1 on success and 0 on failure (Long). VBScript's Not is a bitwise operator, so Not 1 is also true. Compare the value, as in If xpay.Init_TX(LGD_MID) = 0 Then.
  • Protocol value: For ASP, set default_secure_protocols in mall.conf to 2048 (TLS 1.2).

#Notes

  • Application-wide settings: The library sets ServicePointManager.ServerCertificateValidationCallback and ServicePointManager.SecurityProtocol, so they also apply to other HTTPS connections in the same web application. In particular, verify_cert = 0 disables certificate validation for the whole application. Keep verify_cert = 1 in production.
  • Accumulating validation callbacks: The library adds a certificate validation callback on every request. If the application pool runs for a long time without restarting, the callbacks keep accumulating, so keep periodic recycling enabled for the IIS application pool.
  • File encoding: ASP.NET reads .aspx files without a BOM using the server's default character set (CP949 on Korean Windows). The sample .aspx files are saved as UTF-8 with a BOM, so keep the BOM when you edit them.
  • Configuration files and logs: The library reads mall.conf and lgdacom.conf as EUC-KR and writes logs in EUC-KR. Because the settings are ASCII, a UTF-8 mall.conf works correctly; only Korean comments may look garbled.
