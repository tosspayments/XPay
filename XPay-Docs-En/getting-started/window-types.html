#Choose an integration method

You can integrate Toss Payments in four ways. Because the screens you call and the parameters you send depend on the method, decide on the method before you start.

MethodWindow providerCharacteristics
Unified payment windowToss PaymentsProvides everything up to the payment method selection screen. The most common option.
Self-hosted windowCard company or easy payment providerCalls an individual card company's own window or an easy payment service directly.
APINone (merchant page)Collects input on the merchant's own screen without a payment window.
OtherVaries by methodServices provided through a separate URL or the library.

#Unified payment window

The buyer pays through the unified payment window provided by Toss Payments. When the buyer selects a payment method and completes authentication in the window, LGD_PAYKEY is issued, and you request approval with this key. Toss Payments provides both the payment method selection screen and the authentication screen for each payment method, so this method requires the fewest screens on the merchant side.

On PC, the window opens in an iframe; on mobile, it opens as a page navigation. Specify this with LGD_WINDOW_TYPE.

EnvironmentLGD_WINDOW_TYPE
PCiframe
Mobilesubmit

For integration details, see Unified payment window. It covers cards, bank transfers, virtual accounts, gift certificates, and mobile phone payments on one page.

#Self-hosted window (hub type)

Instead of using the unified payment window provided by Toss Payments, you call an individual card company's own window or an easy payment service directly. The merchant builds the payment method selection screen and opens the selected card company's payment window directly. Use this method when you want the payment method selection UI to match your own design.

The approval flow after authentication is the same as in the unified payment window, but you must also send self-hosted window parameters such as LGD_CARDTYPE, LGD_SP_CHAIN_CODE, and LGD_EASYPAY_TRANTYPE.

For integration details, see Self-hosted window.

The legacy self-hosted window method is no longer supported. New integrations use the TWOTR method, which is described in the self-hosted window documentation.

#API

Instead of using a Toss Payments payment window, you collect the required information directly on the merchant page. Because there is no payment window, the merchant collects and sends information such as the card number, expiration date, and the first 2 digits of the card password. Features that do not need a buyer-facing screen, such as cancellations and refunds, also use this method.

Because this method collects card numbers directly, stricter security requirements apply to the merchant server. Before you integrate, review the Merchant server security checklist.

Key integration pages:

  • Card non-authenticated payment — Key-in payment with a card number entered directly
  • Card billing payment — Payment with an issued billing key
  • Cancel and partially cancel — Full or partial cancellation of an approved transaction
  • Issue and change virtual accounts
  • Transaction lookup

#Other

Services provided through a separate URL or the library, such as transaction receipt printing, escrow, transaction reconciliation, and settlement reconciliation. Some of these features are called directly over HTTPS without the XPayClient library, so the call method differs from the three methods above.

  • Daily transaction lookup
  • Daily settlement lookup
  • Daily cash receipt lookup
  • Interest-free installment lookup
  • Escrow
