#XPayClient call pattern

All transactions that use XPayClient follow the same call sequence. Only the parameters you pass with Set() and the parameters you get with Response() differ.

This page covers how to use the library and how pages are organized for each payment type. For transaction parameters, see the transaction reference pages.

#Basic call sequence

java
XPayClient xpay = new XPayClient();

// 1. Initialize
if (!xpay.Init(configPath, CST_PLATFORM)) {
    // Could not read the configuration files. Check the lgdacom.conf and mall.conf installation.
    return;
}

// 2. Start the transaction
xpay.Init_TX(LGD_MID);

// 3. Set request parameters
xpay.Set("LGD_TXNAME", "PaymentByKey");
xpay.Set("LGD_PAYKEY", LGD_PAYKEY);

// 4. Send
if (xpay.TX()) {
    // 5. Check the communication response code
    if ("0000".equals(xpay.m_szResCode)) {
        // 6. Check the transaction response code
        String respCode = xpay.Response("LGD_RESPCODE", 0);
        if ("0000".equals(respCode)) {
            // Payment succeeded
        }
    }
}

#Methods

MethodRole
Init(configPath, CST_PLATFORM)Reads the configuration files. configPath is the absolute path of the lgdacom folder, and CST_PLATFORM is test or service.
Init_TX(LGD_MID)Starts a transaction. Pass the merchant ID.
Set(parameter name, value)Sets a request parameter. Call it as many times as needed.
TX()Sends the request to the Toss Payments server. Returns true on success.
Response(parameter name, 0)Gets a response value. The second argument is the index.
Response_Code() · Response_Msg()Gets the response code and message.
GetHashData(MID, OID, AMOUNT, TIMESTAMP)Generates hash data. See Hash data generation.
GetTimeStamp()Generates a timestamp.
Rollback(reason)Automatically cancels the approved transaction.
ResponseNameCount() · ResponseName(i)Iterates over all response parameters.

#There are two response codes

This is the most common integration mistake. You must check both the communication response code and the transaction response code.
ValueMeaningHow to check
xpay.m_szResCodeCommunication response code. Indicates whether communication with the Toss Payments server succeeded.After calling TX()
LGD_RESPCODETransaction response code. Indicates whether the payment was actually approved.Response("LGD_RESPCODE", 0)

A payment succeeds only when both are 0000. If communication succeeds but the card company declines the approval, m_szResCode is 0000 while LGD_RESPCODE has a different value. If you treat this as a success, you complete an order that was never paid.

#Roll back if merchant processing fails after approval

If approval succeeds but saving to the merchant database fails, you must cancel automatically with Rollback(). If you skip this, the buyer is charged but no order record exists.

java
if ("0000".equals(respCode)) {
    boolean isDBOK = saveOrder();          // Save to the merchant DB
    if (!isDBOK) {
        xpay.Rollback("Merchant DB processing failed [TID:" + tid + "]");
    }
}

#Payment window payments

The buyer completes authentication to receive LGD_PAYKEY, and you request approval with that key. Because authentication and approval are separate, several pages are required.

#PC

Use iframe for LGD_WINDOW_TYPE. The payment window opens on top of the current page.

OrderPageRoleDevelopment
1sample_crossplatformPayment information entry screenReference only
2payreq_crossplatformOpens the payment window and requests authenticationDevelopment required
3(Payment window)The buyer selects a payment method and authenticatesProvided by Toss Payments
4returnurlReceive LGD_PAYKEYDevelopment required
5payresRequests final approval and processes the resultDevelopment required

The call flow is as follows.

  1. Enter the payment request information on the product payment page.
  2. Pass the information to payreq_crossplatform.
  3. payreq_crossplatform opens the unified payment window.
  4. The buyer enters additional information for the payment method and authenticates.
  5. LGD_PAYKEY is delivered to returnurl. Because returnurl is a child page of payreq_crossplatform, it calls the payment_return function of the parent page to pass the authentication key.
  6. payreq_crossplatform passes the authentication result to payres.
  7. payres requests final approval through XPayClient.
  8. Receive and process the approval result.
Set LGD_RETURNURL to the full URL of the page in step 4. For example, https://your-merchant-domain/returnurl.jsp. If you do not set this value, you cannot receive the authentication key.

For parameter definitions, see Unified payment window.

#Mobile

Use submit for LGD_WINDOW_TYPE. The page navigates to the payment window.

The page structure is the same as on PC.

text
sample_crossplatform → payreq_crossplatform → authentication payment window → returnurl → payres

There are two differences from PC.

First, returnurl does not call a function on the parent page. Because the window opens as a page navigation, it passes the authentication result directly to payres.

Second, app card integration parameters are added. These include LGD_KVPMISPWAPURL, LGD_KVPMISPCANCELURL, and LGD_MTRANSFERWAPURL, and they are required for cards and bank transfers. For details, see the payment method sections of Unified payment window.

#Billing key issuance

To make recurring payments without collecting card information every time, you first obtain an LGD_BILLKEY.

The page structure differs from payment window payments. Billing key issuance and approval are separate transactions.

#PC

OrderPageRoleDevelopment
1CardBillingAuth.htmlAuthentication key request entry screenReference only
2CardBillingAuth_ReqOpens the payment window and requests billing key authenticationDevelopment required
3returnurlReceive LGD_BILLKEYDevelopment required
4CardBillingAuth_ResChecks the billing key and authentication resultDevelopment required
5CardAuthRequests approval with the billing key and processes the resultDevelopment required

In the table above, pages 1 to 4 issue the billing key, and page 5 pays with the billing key. Once issued, store the billing key and reuse it for later payments. In other words, you only need to repeat page 5.

For the approval request, use CardAuth for LGD_TXNAME and send the stored LGD_BILLKEY instead of a card number. It uses the same method as card non-authenticated payment, but sends LGD_BILLKEY instead of LGD_PAN.

The issued LGD_BILLKEY is sensitive information equivalent to card data. Store it encrypted and never expose it to the client. See the Merchant server security checklist.

For billing key issuance parameters, see Billing key issuance via payment window. For parameters to pay with an issued billing key, see Card billing payment.

#Mobile

OrderPageRoleDevelopment
1CardBillingAuth.htmlCard information entry screenReference only
2MobileXpay_CardBillingAuthOpens the payment window and requests billing key authenticationDevelopment required
3returnurlReceive LGD_BILLKEYDevelopment required
4MobileXpay_CardBillingAuth_payresChecks the billing key and authentication resultDevelopment required
5CardAuthRequests approval with the billing key and processes the resultDevelopment required

The flow is the same as on PC. The page names differ, and the payment window opens as a page navigation instead of a pop-up. The CardAuth approval step is the same as on PC.

There is one mobile-only parameter.

ParameterDescription
LGD_PAYWINDOWTYPEBilling type for smartphone credit cards. The default is CardBillingAuth_smartphone.

#Encoding

The default encoding of the provided sample pages is EUC-KR.

To use them in a UTF-8 environment, configure the following three settings.

ConfigurationValueLocation
When opening the payment windowUTF-8 for LGD_ENCODINGRequest parameters
When receiving the authentication resultUTF-8 for LGD_ENCODING_RETURNURLRequest parameters
When processing the final payment resultoutput_UTF8=1mall.conf

If any of the three is missing, Korean text is garbled. For details, see Configure conf files.
