#Merchant server security checklist

Check the following items before you integrate payments. In particular, you must check Configuration file placement, because it directly affects exposure of the merchant key.

#Configuration file and log placement

This is the most important item. mall.conf stores the production merchant ID (MID) and merchant key (mertkey). If these values are exposed, a third party can request transactions, including payment cancellations.

Place mall.conf and log_dir in a path that is not accessible from the web. log_dir stores the logs of approval requests and results, so it also contains sensitive payment information.

#Web-accessible paths (do not place files here)

EnvironmentWeb-accessible path
PHP + ApacheUnder DOCUMENT_ROOT
Java (JSP)Under CONTEXT ROOT
ASP · ASP.NET + IISUnder wwwroot

#How to check

If the file contents appear when you open the following address in a browser, the file is placed incorrectly.

text
https://your-merchant-domain/lgdacom/conf/mall.conf

The correct result is 403 Forbidden or 404 Not Found. If the contents appear, move the files immediately and request a new merchant key.

For placement details, see Configure conf files.

#Merchant key usage principles

  • Use the merchant key only on the server. Never put it in HTML, JavaScript, or app code.
  • Generate hashes on the server as well. When you use xpay.GetHashData(), the library reads the merchant key from mall.conf, so you do not need to write the value in your code. For details, see Hash data generation.
  • Manage test and production merchant keys separately.
  • Never leave archive passwords or merchant keys in plain text in documents, folder names, or repositories.

#HTTP protocol

#Use HTTPS only

You must call Toss Payments APIs over HTTPS.

HTTPS is the secure version of HTTP. Data exchanged over HTTP is unencrypted plaintext and can leak personal information. Therefore, you must use HTTPS, a protocol with enhanced security that protects buyers' payment and personal information.

#Only TLS 1.2 or later is supported

TLS (Transport Layer Security) is a secure communication protocol. Toss Payments APIs support only TLS 1.2 or later.

SSL/TLS versions earlier than TLS 1.2 are not supported because they are insecure. Check that the HTTP client environment on the merchant server supports TLS 1.2 or later.

Each language has minimum version requirements for using TLS 1.2. See Installation and environment.

#Use secure cipher suites

Only the following cipher suites, or stronger algorithms, are supported.

Cipher suite A set that defines which algorithms are combined for key exchange, encryption, and integrity checks in TLS/SSL communication.

TLS 1.3

  • TLS_AES_128_GCM_SHA256
  • TLS_AES_256_GCM_SHA384
  • TLS_CHACHA20_POLY1305_SHA256

TLS 1.2

  • ECDHE-ECDSA-AES128-GCM-SHA256
  • ECDHE-RSA-AES128-GCM-SHA256
  • ECDHE-ECDSA-AES128-SHA256
  • ECDHE-RSA-AES128-SHA256
  • ECDHE-ECDSA-AES256-GCM-SHA384
  • ECDHE-RSA-AES256-GCM-SHA384
  • ECDHE-ECDSA-AES256-SHA384
  • ECDHE-RSA-AES256-SHA384

#Response forgery verification

When you receive a payment response, you must recalculate LGD_HASHDATA and check that it matches the response value. If the values differ, the response is forged, so do not treat the payment as successful.

For the verification method, see the response hash section of Hash data generation.

#Firewall settings

You must allow IPs in your firewall to call the payment API and receive virtual account deposit notifications. For the IPs, see Firewall and IP information.

Virtual account deposit notifications (LGD_CASNOTEURL) can use only standard ports. Notifications cannot be received on ports other than 80 for HTTP and 443 for HTTPS.
