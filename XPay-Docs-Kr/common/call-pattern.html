#XPayClient 호출 패턴

XPayClient를 사용하는 모든 거래는 동일한 호출 순서를 따릅니다. 달라지는 것은 Set() 으로 전달하는 파라미터와 Response() 로 꺼내는 파라미터뿐입니다.

이 페이지는 라이브러리 사용법과 결제 유형별 페이지 구성을 다룹니다. 거래별 파라미터는 각 거래 레퍼런스 문서를 참고하세요.

#기본 호출 순서

java
XPayClient xpay = new XPayClient();

// 1. 초기화
if (!xpay.Init(configPath, CST_PLATFORM)) {
    // 환경파일을 읽지 못했습니다. lgdacom.conf, mall.conf 설치 상태를 확인하세요.
    return;
}

// 2. 거래 시작
xpay.Init_TX(LGD_MID);

// 3. 요청 파라미터 설정
xpay.Set("LGD_TXNAME", "PaymentByKey");
xpay.Set("LGD_PAYKEY", LGD_PAYKEY);

// 4. 전송
if (xpay.TX()) {
    // 5. 통신 응답코드 확인
    if ("0000".equals(xpay.m_szResCode)) {
        // 6. 거래 응답코드 확인
        String respCode = xpay.Response("LGD_RESPCODE", 0);
        if ("0000".equals(respCode)) {
            // 결제 성공
        }
    }
}

#메소드

메소드역할
Init(configPath, CST_PLATFORM)환경설정 파일을 읽습니다. configPath 는 lgdacom 폴더의 절대경로, CST_PLATFORM 은 test 또는 service 입니다.
Init_TX(LGD_MID)거래를 시작합니다. 상점아이디를 전달합니다.
Set(파라미터명, 값)요청 파라미터를 설정합니다. 필요한 만큼 반복 호출합니다.
TX()토스페이먼츠 서버로 전송합니다. 성공하면 true 를 반환합니다.
Response(파라미터명, 0)응답값을 꺼냅니다. 두 번째 인자는 인덱스입니다.
Response_Code() · Response_Msg()응답코드와 메시지를 꺼냅니다.
GetHashData(MID, OID, AMOUNT, TIMESTAMP)해쉬데이터를 생성합니다. 해쉬데이터 생성 참고
GetTimeStamp()타임스탬프를 생성합니다.
Rollback(사유)승인된 거래를 자동취소합니다.
ResponseNameCount() · ResponseName(i)응답 파라미터 전체를 순회합니다.

#응답코드는 두 개입니다

가장 자주 발생하는 연동 실수입니다. 통신 응답코드와 거래 응답코드를 둘 다 확인해야 합니다.
값의미확인 방법
xpay.m_szResCode통신 응답코드. 토스페이먼츠 서버와 통신이 정상이었는지TX() 호출 후
LGD_RESPCODE거래 응답코드. 결제가 실제로 승인되었는지Response("LGD_RESPCODE", 0)

둘 다 0000 이어야 결제 성공입니다. 통신은 성공했지만 카드사 승인이 거절된 경우 m_szResCode 는 0000, LGD_RESPCODE 는 다른 값이 됩니다. 이때 성공으로 처리하면 결제되지 않은 주문을 완료 처리하는 사고가 발생합니다.

#승인 후 상점 처리가 실패하면 되돌리세요

승인은 성공했는데 상점 DB 저장이 실패하면 Rollback() 으로 자동취소해야 합니다. 이 처리를 빠뜨리면 구매자는 결제됐는데 주문 기록이 없는 상태가 됩니다.

java
if ("0000".equals(respCode)) {
    boolean isDBOK = saveOrder();          // 상점 DB 저장
    if (!isDBOK) {
        xpay.Rollback("상점 DB 처리 실패 [TID:" + tid + "]");
    }
}

#결제창 결제

구매자 인증을 거쳐 LGD_PAYKEY 를 받고, 그 키로 승인을 요청하는 방식입니다. 인증과 승인이 분리되어 있어 페이지가 여러 개 필요합니다.

#PC

LGD_WINDOW_TYPE 은 iframe 을 사용합니다. 결제창이 현재 페이지 위에 겹쳐 열립니다.

순서페이지역할개발
1sample_crossplatform결제 정보 입력 화면참고용
2payreq_crossplatform결제창 호출 및 인증 요청개발 필요
3(결제창)구매자가 결제수단 선택 후 인증토스페이먼츠 제공
4returnurlLGD_PAYKEY 수신개발 필요
5payres최종 승인 요청 및 결과 처리개발 필요

호출 흐름은 아래 순서입니다.

  1. 상품결제정보 페이지에서 결제 요청 정보를 입력합니다.
  2. 입력 정보를 payreq_crossplatform 으로 전달합니다.
  3. payreq_crossplatform 에서 통합결제창을 호출합니다.
  4. 구매자가 결제수단별 추가 정보를 입력하고 인증합니다.
  5. returnurl 로 LGD_PAYKEY 가 전달됩니다. returnurl 은 payreq_crossplatform 의 자식 페이지이므로, 부모 페이지의 payment_return 함수를 호출해 인증키를 전달합니다.
  6. payreq_crossplatform 이 인증 결과를 payres 로 전달합니다.
  7. payres 에서 XPayClient로 최종 승인을 요청합니다.
  8. 승인 결과를 받아 처리합니다.
LGD_RETURNURL 에는 4번 페이지의 전체 URL을 설정해야 합니다. 예를 들어 https://내가맹점도메인/returnurl.jsp 형태입니다. 이 값을 설정하지 않으면 인증키를 받을 수 없습니다.

파라미터 정의는 통합결제창 결제를 참고하세요.

#모바일

LGD_WINDOW_TYPE 은 submit 을 사용합니다. 결제창으로 페이지가 이동합니다.

페이지 구성은 PC와 같습니다.

text
sample_crossplatform → payreq_crossplatform → 인증결제창 → returnurl → payres

PC와 다른 점은 두 가지입니다.

하나. returnurl 이 부모 페이지의 함수를 호출하지 않습니다. 페이지 이동 방식이므로 인증 결과를 직접 payres 로 전달합니다.

둘. 앱카드 연동 파라미터가 추가됩니다. LGD_KVPMISPWAPURL, LGD_KVPMISPCANCELURL, LGD_MTRANSFERWAPURL 등이며, 카드와 계좌이체에서 필수입니다. 자세한 내용은 통합결제창 결제의 결제수단별 섹션을 참고하세요.

#빌링 빌키 생성

카드 정보를 매번 입력받지 않고 반복 결제하기 위해 LGD_BILLKEY 를 먼저 발급받는 방식입니다.

결제창 결제와 페이지 구성이 다릅니다. 빌키 발급과 승인이 별개의 거래입니다.

#PC

순서페이지역할개발
1CardBillingAuth.html인증키 요청 입력 화면참고용
2CardBillingAuth_Req결제창 호출 및 빌링키 인증 요청개발 필요
3returnurlLGD_BILLKEY 수신개발 필요
4CardBillingAuth_Res빌링키 및 인증 결과 확인개발 필요
5CardAuth빌링키로 승인 요청 및 결과 처리개발 필요

1~4번이 빌키 생성이고, 5번이 빌키로 결제입니다. 빌키는 한 번 발급받으면 저장해두고 이후 결제에 재사용합니다. 즉 5번만 반복 호출하면 됩니다.

승인 요청은 LGD_TXNAME 에 CardAuth 를 사용하며, 카드번호 대신 저장해 둔 LGD_BILLKEY 를 전달합니다. 카드 비인증 결제와 같은 메소드를 쓰지만 LGD_PAN 이 아니라 LGD_BILLKEY 를 보내는 점이 다릅니다.

발급받은 LGD_BILLKEY 는 카드 정보에 준하는 민감 정보입니다. 암호화해 저장하고, 클라이언트에 노출하지 마세요. 가맹점 서버 보안 점검을 참고하세요.

빌키 발급 파라미터는 결제창 빌링키 발급, 발급된 빌키로 결제하는 파라미터는 카드 빌링 결제를 참고하세요.

#모바일

순서페이지역할개발
1CardBillingAuth.html카드 정보 입력 화면참고용
2MobileXpay_CardBillingAuth결제창 호출 및 빌링키 인증 요청개발 필요
3returnurlLGD_BILLKEY 수신개발 필요
4MobileXpay_CardBillingAuth_payres빌링키 및 인증 결과 확인개발 필요
5CardAuth빌링키로 승인 요청 및 결과 처리개발 필요

흐름은 PC와 같습니다. 페이지 이름이 다르고, 결제창이 팝업이 아니라 페이지 이동 방식으로 열립니다. 승인 단계의 CardAuth 는 PC와 동일합니다.

모바일 전용 파라미터가 하나 있습니다.

파라미터설명
LGD_PAYWINDOWTYPE스마트폰 신용카드 빌링타입 정보입니다. 기본값은 CardBillingAuth_smartphone 입니다.

#인코딩

제공되는 샘플 페이지의 기본 인코딩은 EUC-KR 입니다.

UTF-8 환경에서 사용하려면 두 곳을 설정해야 합니다.

설정값위치
결제창 호출 시LGD_ENCODING 에 UTF-8요청 파라미터
인증결과 수신 시LGD_ENCODING_RETURNURL 에 UTF-8요청 파라미터
최종 결제결과 처리 시output_UTF8=1mall.conf

세 곳 중 하나라도 빠지면 한글이 깨집니다. 자세한 내용은 conf 설정을 참고하세요.
